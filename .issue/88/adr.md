# ADR — Issue #88: ファイル・ディレクトリの検索機能を追加する

## ADR-001: フィルタリングはクライアント側で完結させる

### Status
Proposed

### Context
ファイルツリーの検索をクライアント側フィルタで行うか、サーバー側に検索 API を追加するかの選択。ツリーデータは `initialState.tree` としてクライアントに渡され `DirectoryApp` の state で保持されている。Issue 本文でも「まずはクライアント側フィルタで十分そう」と明記されている。

### Decision
クライアント側フィルタを採用する。`src/core/file-tree.ts` に純粋関数 `filterFileTree` を追加し、`DirectoryApp` で保持しているツリーを絞り込む。

### Consequences
- 良い点: サーバー往復不要で即時フィルタ。`core` の純粋関数として実装でき、ユニットテストが容易。
- トレードオフ: 非常に大規模なディレクトリでは毎キーストロークのフィルタコストが問題になりうる。`useMemo` で抑制し、顕在化したらサーバー側検索を別 Issue で検討する。

## ADR-002: 検索対象はノードの name のみ

### Status
Proposed

### Context
検索マッチング対象をファイル/ディレクトリの `name` のみにするか、`path` 全体（親ディレクトリ名含む）にするか。

### Decision
`name` を対象とする。内部マッチャ（`matchesQuery`）を一箇所に集約し、将来パス全体対応へ拡張しやすい構造にする。

### Consequences
- 良い点: Issue 本文の「名前で検索」という主題に合致。深い階層の親ディレクトリ名に意図せずヒットする直感に反する結果を避けられる。親パスはツリー構造で別途表現される。
- トレードオフ: 「親ディレクトリ名でまとめて絞る」用途は直接はできない。マッチャ集約により後から拡張可能。

## ADR-003: ディレクトリ自身がマッチしたら配下を全保持（案A）

### Status
Proposed

### Context
親パス保持のためボトムアップ再帰でフィルタする際、「ディレクトリ自身がマッチした場合の子の扱い」に2案がある。
- 案A: ディレクトリ自身マッチ → 配下を全保持（その中を辿れる）。
- 案B: ディレクトリ自身マッチでも子は再帰フィルタ結果のみ残す。

### Decision
案A を採用する。ディレクトリ名で絞ったらその中身を見たい、という挙動が自然。

### Consequences
- 良い点: ディレクトリ名検索の結果が直感的。
- トレードオフ: ディレクトリ名にマッチすると配下が全部出るため、結果件数が多くなる場合がある。テストで挙動を固定する。
- 前提: `src/lib/file-tree.ts` の `processEntries` は子を持つディレクトリのみノード化する（空ディレクトリ・対象ファイルを含まないディレクトリは除外）。よって実ツリーに「空ディレクトリ」は現れない。テストフィクスチャもファイルを子に持つディレクトリ構造で固定する。

## ADR-005: 検索中はトグル（onToggle）も無効化する

### Status
Proposed

### Context
ADR-004 で検索中は `isOpen` を `() => true` に差し替えて全展開する。しかし `onToggle` をそのまま渡すと、検索中にディレクトリヘッダをクリックした際に見た目は全展開のまま変わらないのに localStorage の折りたたみ state だけが書き換わる（不可視の副作用）。

### Decision
検索アクティブ時は `onToggle` も `undefined`（no-op）に差し替える。`onToggle={isSearching ? undefined : fileTree.toggle}`。

### Consequences
- 良い点: 「検索中はトグル無効・全展開」という意図がコードで明示され、不可視の localStorage 汚染を防げる。
- トレードオフ: なし（検索中はそもそも全展開なのでトグルに意味がない）。

## ADR-006: `/` ショートカットのために `useSidebar` に `open` アクションを追加

### Status
Accepted（実装時の判断）

### Context
`/` ショートカットでサイドバーが閉じている場合に開くコールバックを `DirectoryApp` から `useSearchShortcut` に渡す必要がある。しかし既存の `useSidebar` は `toggle` / `close` のみを公開しており、明示的に「開く」 API が無かった。`toggle` を渡すと、既に開いている場合に閉じてしまう副作用がある。

### Decision
`useSidebar` に `open`（冪等にサイドバーを開く）アクションを追加し、`useSearchShortcut(sidebar.open)` として渡す。`open` は `useCallback` でラップしてあるため参照が安定し、`useSearchShortcut` の `useEffect` 依存も安定する。デスクトップでは `close` と対称に `localStorage` の `sidebar-open` を `"true"` に更新する。

### Consequences
- 良い点: 「開く」意図が明示的になり、`toggle` の誤った副作用（開いている時に閉じる）を避けられる。参照が安定しリスナ再登録も起きない。
- トレードオフ: `SidebarActions` 型の表面積が増えるが、自然な追加で既存呼び出しには影響しない。

## ADR-004: 検索アクティブ時は折りたたみ状態を無視して全展開

### Status
Proposed

### Context
`useFileTreeState` がディレクトリの折りたたみ状態を localStorage に永続化している。検索でマッチしたノードへのパスを見せるには、折りたたまれたディレクトリも展開して表示する必要がある。

### Decision
検索アクティブ時は `Sidebar` に渡す `isOpen` を `() => true`（常に開いている）に差し替える。検索クリア後は元の `isOpen` に戻す。折りたたみ state 自体は破壊しない。

### Consequences
- 良い点: マッチへのパスが必ず可視化され、受け入れ条件「親パスが維持される」を満たす。検索クリアで元の折りたたみ状態に戻る。
- トレードオフ: 検索中に `onToggle` が呼ばれても見た目は変わらない（全展開のまま）。トグル自体は localStorage に書かれるので動作確認で挙動を確認する。

---
