# plan レビュー round-1 — 観点: Issue の要件カバレッジ・スコープ整合性

**対象:** `.issue/102/plan.md` / `.issue/102/adr.md`
**Issue:** #102（Ctrl+C でシャットダウンが無限ハングすることがある）
**レビュー日:** 2026-07-25

## 前提: Issue の要件は 1 つだけ

Issue 本文に受け入れ条件の記載は無く、コメントもゼロ。読み取れる要件は次の 1 行に尽きる。

> `Ctrl+C`（SIGINT）を 1 回押したら、SSE 接続中でも peek プロセスが有限時間で終了すること。

修正案 1〜3 は「いずれか」と明記された**手段の候補**であり、要件ではない。したがって「修正案 3 を採らない」ことは、それ自体では要件違反にならない（→ 判定は S-005）。

以下のレビューはすべて「この 1 要件を確実に満たすか」を基準に判定している。

## 判定サマリー（親指示の 5 論点に対する回答）

| 論点 | 判定 |
|---|---|
| AC-1 だけで要件は満たされるか | **満たされる。** 構造対策（AC-3/4/5）は要件充足には不要な再発防止（後述「AC-1 の十分性の検証」） |
| AC-7（型述語化）は Issue が求める変更か | **求めていない。受け入れ基準としては不適格（S-001）。** 変更自体は同じ行を書き換えるついでなので実施可、ただし AC からは外す |

## 問題点（要修正）

- **[P-001]** AC-5 の後半「ブラウザ `EventSource` が再接続ループに入らない」は**事実として偽**であり、検証すると正しい実装でも不合格になる。
  - 理由: このプロジェクトのクライアントは native `EventSource` の自動再接続に依存していない。`src/client/lib/sse.ts:55-79` は `onerror` で `evtSource.close()` した後、**自前で `setTimeout(connect, delay)` を張って新しい `EventSource("/sse")` を作る**。`src/server/renderer/html-document.tsx:34-43` のインラインスクリプトも同一構造。
    したがって 503 を受けても、200 + 即クローズを受けても、**観測される挙動は同一**（`onerror` 発火 → 自前リトライ、`SSE_MAX_RETRIES = 10` 上限、1s→2s→4s→8s→16s→30s×5 の計 10 回）。native の「非 2xx は恒久 CLOSED」仕様は、`onerror` が独自に再接続する以上この実装には効かない。逆に「200 + 即クローズなら native の再接続ループに入る」も、`onerror` 冒頭の `es.close()` が native 再接続を打ち切るため成立しない。
    plan.md 自身も L102 で「我々の `onerror` 側のリトライも 10 回上限で収束する」と書いており、AC-5 の「再接続ループに入らない」と**内部矛盾している**。
    さらにステップ 7 の手動確認「DevTools の Network で `/sse` の再試行が発生しないことを目視する」（L357）は、実装が設計どおり正しくても**必ず失敗する**（再試行は最大 10 回発生し、`ERR_CONNECTION_REFUSED` になる）。検証手順として成立していない。
  - 提案:
    1. AC-5 を「シャットダウン開始後の `/sse` は 503 を返す（`sse.app.request("/sse")` で検証）」に縮める。後半の再接続に関する主張は削除する。
    2. 必要ならクライアント側の事実を別行に分離する: 「サーバー終了後のクライアント再接続は既存の 10 回上限バックオフで収束し、無限リトライにならない（既存挙動、本 Issue で変更しない）」。
    3. plan.md L102・L183、ADR-003 の「非 2xx なら再接続しない」を根拠とする記述を差し替える。**503 を選ぶ判断自体は維持してよい**が、正しい根拠は「ストリームを一切生成しない（軽い）」「意味論的に正しいステータス」「クライアント挙動はどちらでも同じなので害が無い」の 3 点。
    4. ステップ 7 の目視項目を「`/sse` の再試行が最大 10 回で止まり、無限に続かないこと」に書き換える。

- **[P-002]** 調査結果に**第 2 の SSE クライアント実装**が抜けている。
  - 理由: `src/server/renderer/html-document.tsx:14-47` に、HTML ファイルプレビュー用のインライン SSE 再接続スクリプトが存在する（`SSE_MAX_RETRIES` / `SSE_INITIAL_RETRY_MS` / `SSE_MAX_RETRY_MS` を埋め込む独立実装）。Issue 本文が引用している `var es = new EventSource("/sse");` は `src/client/lib/sse.ts`（`const evtSource`）ではなく**こちらのコード**と一致する。
    plan.md の「関連ファイル」表（L41-53）にも、スコープ節の「含まれないもの」（L31、`src/client/lib/sse.ts` のみを名指し）にも登場しない。P-001 の誤認はこの調査漏れに起因している。また `src/server/index.test.ts` が使う `contentType: "html"` はまさにこの実装が載るモードである。
  - 提案: 関連ファイル表に `src/server/renderer/html-document.tsx`（HTML ファイルモードの SSE 再接続スクリプト。`src/client/lib/sse.ts` と同等の独自リトライを持つ）を追加し、スコープの「含まれないもの」を「クライアント側 SSE 再接続ロジック（`src/client/lib/sse.ts` **および** `src/server/renderer/html-document.tsx` のインラインスクリプト）」に修正する。

- **[P-003]** 受け入れ基準とステップの紐づけに誤りと漏れがある。
  - 理由: 親指示の「基準と実装ステップの紐づけが正しいか」に対する具体的な不整合が 3 件ある。
    - **AC-9 の対応ステップが「6」になっているが、手動確認はステップ 7**。ステップ 6 は `withTimeout` の単体テストで、AC-9 とは無関係。
    - **AC-1 の対応ステップに「6」が無い**。ステップ 6 の説明自身が「AC-1 / AC-2 の唯一の決定的な自動検証」（L316）と書いており、AC-1 を検証する唯一の手段が紐づいていない。
    - **AC-2（タイムアウト時の `logger.warn`）に検証ステップが 1 つも紐づいていない**。ステップ 7 が「警告が出るかどうかを記録する」と明記しているのに対応ステップ欄は「1, 4」。加えて「テスト方針」の自動テスト表にも AC-2 の行が無く、`withTimeout` の単体テストは呼び出し側の `logger.warn` を通らないため、**AC-2 は自動でも手動でも検証が定義されていない状態**。
  - 提案: AC-1 → `1, 4, 6`、AC-2 → `1, 4, 7`（手動記録であることを明示）、AC-9 → `7` に修正する。AC-2 を自動検証したい場合は、ステップ 5 に `shutdown({ timeoutMs: 0 })` + `logger.warn` スパイのケースを足す（`timeoutMs: 0` なら `close()` の解決より先に必ずタイマーが発火するか要確認。確実性が担保できないなら手動記録のままでよいが、その場合は「AC-2 は手動確認のみ」と明記すること）。

- **[P-004]** Issue の唯一の要件を**プロセスレベルで**表す受け入れ基準が無い。
  - 理由: AC-1 が保証するのは `shutdown()` の Promise が有限時間で settle することまでで、要件は「peek **プロセス**が終了すること」。そこに至る鎖は `await server.shutdown()` → `outro()` → `process.exit(0)`（`src/index.ts:181-186`）で、plan は「CLI 変更なし」としている。この鎖を検証する基準は AC-9（手動）しか無く、その AC-9 は P-003 / P-005 のとおり不備がある。
    要件の中心に自動検証が 1 つも無い状態は、受け入れ基準として弱い。なお `shutdown()` が reject した場合も CLI が `catch` して `process.exit(0)` に到達するため実装上は問題ないが、**その経路も基準に書かれていない**。
  - 提案: 次の AC を追加する。
    > AC-0: SSE 接続が張られた状態の peek プロセスに SIGINT を 1 回送ると、3 秒以内に exit code 0 で終了する（`shutdown()` が resolve でも reject でも成立すること）。

    検証手段は 2 択。
    - **(a) 自動化する（推奨）**: `child_process.spawn` で `tsx --import ./src/loaders/css.mjs src/index.ts <fixture> --port <free> --no-open` を起動し、`fetch("/sse")` でヘッダまで受け取ってから `child.kill("SIGINT")`、`close` イベントまでの経過時間と exit code を assert する。`vitest.config.ts` の `testTimeout` は 30000ms あるので枠は足りる。これで初めて「Ctrl+C で終了する」が回帰テストになる。
    - **(b) 手動に留める**: AC-9 を AC-0 の検証手段として明示的に紐づけ、「自動テストでは担保しない」ことをテスト方針に書く。
  - 補足: (a) を採るなら AC-9 の 10 回反復は不要になり、手動確認は「実ブラウザでの挙動確認」だけに縮められる。

- **[P-005]** AC-9 は基準として二重に不備がある（閾値の自己矛盾 + 証明力ゼロ）。
  - 理由:
    1. **閾値が設計と矛盾している。** `SHUTDOWN_TIMEOUT_MS = 2_000` なので、タイムアウトが発火した場合の終了は「2 秒 + `outro()` + `process.exit`」で **2 秒を必ず超える**。つまり設計どおりに打ち切りが働いた正常なケースで AC-9（「毎回 2 秒以内」）が不合格になる。AC-1 が自ら「2 秒 + α」と書いているのに AC-9 だけ「2 秒以内」になっている。
    2. **10 回の成功は「直った」証明にならない。** 元の事象は Issue 本文にあるとおり「普段は正常に終了する」低頻度のタイミング依存事象で、母数不明の稀事象に対して n=10 の成功はほぼ何の情報も持たない（真の発生率が 1% なら 10 回連続成功の確率は 90%）。この基準を「要件を満たした証拠」として使うと誤った安心を生む。
       ただしこれは AC-9 を捨てるべきという意味ではない。**本計画で終了性を保証しているのは統計ではなく構造**（`withTimeout` + `process.exit(0)`）であり、その決定的検証はステップ 6 の単体テスト（と P-004 の AC-0）が担う。AC-9 の役割はそこではなく、(i) 正常系（ライブリロード・通常終了）を壊していないことの非退行確認と、(ii) **警告ログが出るか出ないかの記録**（= 真因が残っているかの切り分け）にある。plan.md の「リスクと注意点」L336 は正しくその位置づけを書いているのに、AC-9 の本文がそれを反映していない。
  - 提案: AC-9 を次のように書き換える。
    > AC-9（手動・非退行確認）: `peek . --host 0.0.0.0 --port 3009` をブラウザタブ常時オープンで起動し、Ctrl+C を 10 回試行する。(a) 毎回 3 秒以内に `Server stopped. Bye!` が出て終了する、(b) 各試行で `[peek] ... did not close within ...` 警告の有無を記録する。**本基準は「ハングが直った」ことの証明ではなく、正常系の非退行確認と真因切り分けのための観測である**（終了性の保証は AC-0 / AC-1 が担う）。

    あわせて AC-1 の「既定 2 秒 + α」と表記を揃えること。

## 改善提案（検討推奨）

- **[S-001]** AC-7（`in` ナローイングの型述語化）を受け入れ基準から外し、「付随整理」に降格する。
  - 理由: 受け入れ基準としての体をなしていない。AC-7 の検証条件は「`pnpm typecheck` が通る」だが、**現状の `in` ナローイングでも typecheck は通る**（`src/server/index.ts:196` は実際にコンパイルされている）。つまり変更前後で常に真になる条件であり、何も検証していない。由来欄も「CLAUDE.md（型安全性）／親指示」で、Issue 由来ではないことを自認している。
    一方で変更そのものを止める理由も薄い。ステップ 4 は `shutdown()` 本体をまるごと書き換えるため当該行は必ず触る。差分は「モジュールスコープに 3 行の述語 + doc コメント」で、挙動は不変、リスクはほぼゼロ。別 Issue に切り出すコストの方が高い。
  - 提案: AC 表から AC-7 を削除し、スコープ節に「含まれるもの（付随整理）: `in` ナローイングの型述語化 — 同一行を書き換えるついでの型安全化であり、要件充足には不要」と明記する。ステップ 4 の記述はそのままでよい。

- **[S-002]** ADR-005（`ServerInstance` から `close` / `sseCloseAll` を削除）は**採用してよい**。ただし要件外であることを明記する。
  - 理由: 2 つの削除は性質が違う。
    - `sseCloseAll` の削除は**改名の必然的帰結**。ADR-003 で `closeAll` が終端操作 `shutdown` になる以上、`sseCloseAll` を公開したままだと「SSE だけ永久に 503、サーバーは生存」という不整合な状態を外部から作れる型が残る。整合性のために削除するのは筋が通っている。
    - `close` の削除は純粋な未使用整理。`grep` で確認したとおり `src/` 内の呼び出しは `shutdown()` の内部のみで、テストも `shutdown` しか使っていない。`package.json` に `main` / `exports` が無く `bin` のみなのも確認済み（型を import できる外部コンシューマは存在しない）。削除は 2 行、呼び出し元ゼロ、リスクゼロ。
    → どちらも切り出す価値より、切り出したときの追跡コストの方が高い。**別 Issue 化は不要。**
  - 提案: ただし現状 ADR-005 に対応する AC が 1 つも無く、スコープ節にも記載が無いため「無自覚に混入したスコープ外変更」に見える。S-001 と同じ「含まれるもの（付随整理）」節に、`sseCloseAll` の削除は ADR-003 の帰結、`close` の削除は未使用整理、と理由付きで明記する。AC は足さなくてよい（AC-8 の既存テスト通過で十分カバーされる）。

- **[S-003]** ステップ 2 の「`broadcast()` を `shuttingDown` 時に no-op にする」は削除してよい。
  - 理由: **要件充足に不要な上、挙動が変わらない。** `sse.shutdown()` は `clients` を `clear()` するので、以後 `broadcast()` は空の `Set` を回るだけの no-op。新規 client は 503 / 再チェックで登録されないので `clients` が再び埋まることもない。つまりフラグ判定を足しても実行結果は 1 ビットも変わらない。
    加えてステップ 3 の追加テスト「`shutdown()` 後の `broadcast()` が throw しない」は、既存テスト `broadcast does not throw with no clients`（`src/server/routes/sse.test.ts:23-28`）と実質同一であり、カバレッジも増えない。
    対応する AC も無い（AC-4/AC-5 は `/sse` の話）ため、これも無追跡のスコープ外変更にあたる。
  - 提案: ステップ 2 の最終項目とステップ 3 の対応テストを削除する。「契約として明確にする」ことが目的なら、コード変更ではなく `shutdown()` の doc コメントに「以後 `broadcast()` は no-op になる」と 1 行書けば足りる。

- **[S-004]** 実装を「要件充足」と「再発防止・整理」の 2 段に分けてコミット（できれば PR も）を分割する。
  - 理由: 後述「AC-1 の十分性の検証」のとおり、Issue の要件は**第 1 段だけで満たされる**。分割しておけば、第 2 段で回帰が出ても要件充足分を残せる／レビューで「なぜバグ修正でこれだけ差分が出るのか」という論点を切り離せる。
    - 第 1 段（要件）: ステップ 1（`withTimeout`）、ステップ 6（単体テスト）、ステップ 4 のうち「順序変更 + `withTimeout` 適用 + `logger.warn` + `close` の memo 化」、P-004 の AC-0 テスト。
    - 第 2 段（再発防止・整理）: ステップ 2/3（SSE フラグ + 改名）、ステップ 4 のうち型述語化と `ServerInstance` 縮小、ステップ 5 の AC-3 テスト。
  - 補足: 順序は逆にしない。要件を満たす変更を先に着地させること。

- **[S-005]** ADR-002 は Issue 修正案 3 の**前半しか論駁していない**。
  - 理由: 修正案 3 は「`closeIdleConnections()` の併用」**および**「close 完了までの間に張られた接続も確実に破棄する」の 2 部構成。ADR-002 は前者（`closeAllConnections()` の上位互換性）だけを扱い、後者に触れていない。読み手には「修正案 3 を丸ごと却下した」ように見え、Issue の意図に反した判断と誤読されうる。
    実際には後半の懸念は ADR-002 の順序変更（`server.close()` を破棄操作より前に置く）で**解消される**——リスナーが先に閉じる以上「close 完了までの間に新たに accept される接続」が存在しなくなる。つまり修正案 3 の後半は**別の手段で満たされている**のであって、却下されたのではない。
  - 提案: ADR-002 の Decision に 1 段落追加する。「修正案 3 の後半（close 完了までの間に張られた接続の破棄）は、リスナーを先に閉じる順序変更により『そもそも新規接続が accept されない』形で解消される。`closeIdleConnections()` の併用のみを不採用とする。」

- **[S-006]** AC-6 は本 Issue で新たに満たす基準ではなく、**既存挙動の回帰防止**である旨を由来欄に反映する。
  - 理由: keep-alive の中断は現行コードの per-client `AbortController`（`src/server/routes/sse.ts:53,78`）で既に成立しており、本計画はこれを変えない（ADR-003 が「主: per-client abort」と明記）。由来欄が「Issue 症状」だと「今回直す症状」に見えるが、実際は AC-8 と同じ「回帰防止」カテゴリ。
  - 提案: AC-6 の由来を「回帰防止（既存の per-client abort の維持）」に変更する。要件カバレッジの見通しが正確になる。

- **[S-007]** `withTimeout` を `src/lib/` に置く根拠の出典が不正確。
  - 理由: plan.md L132 / ADR-001 が引く `.issue/89/adr.md` ADR-001 は「プロジェクト識別子は targetPath の SHA-256 先頭 16 hex 文字」という別テーマの ADR で、そこに書かれているのは「`src/core/` はフレームワーク/ランタイム非依存層」という理由づけであって「`core` はクライアントバンドルに入りうる層」ではない。引用としてずれている。
    なお**結論（`src/lib/` に置く）は正しい**。`timer.unref()` は Node 専用 API で、DOM の `setTimeout` の戻り値には存在しない。この関数はランタイム非依存ではないので `src/core/` は不適。
  - 提案: 根拠を「`timer.unref()` が Node 専用 API であり、`src/core/` の『ランタイム非依存』要件（`.issue/89/adr.md` ADR-001 の区分）を満たさないため」に書き換える。

## AC-1 の十分性の検証（親指示への回答の根拠）

「AC-1 だけで要件を満たすか」をコードで確認した結果、**満たす**。根拠は次の鎖がすべて有限であること。

1. `shutdown()` の 1〜4 はすべて同期。`watcher.close()` は同期（`src/lib/watcher.ts:70-73` — フラグを立てて `watcher.close()` を呼ぶだけ）、`sse.shutdown()` も同期ループ、`closeAllConnections()` も同期。ブロックする箇所が無い。
2. 唯一の待機点 `await withTimeout(closing, 2_000)` が有界（AC-1）。
3. `withTimeout` が reject を透過しても、`src/index.ts:180-184` の `try/catch` が受けて処理を継続する。
4. `src/index.ts:186` の `process.exit(0)` は残存ハンドル・生存ソケットの有無に関わらずプロセスを落とす。

したがって「Ctrl+C で必ず終了する」は **ステップ 1 + ステップ 4 の一部（`withTimeout` 適用）+ 既存 CLI** だけで成立する。

一方、構造対策（ADR-002 の順序変更、ADR-003 のフラグ + 二重チェック）は**要件充足には寄与しない**。plan.md の「調査結果」L83-89 が示すとおり Issue 記載のレースは現行 Hono / node-server では成立せず、フラグが実際に効く経路（`clients.clear()` 後に `clients.add` が走る）は、将来 Hono のディスパッチや `shutdown()` に `await` が入った場合にのみ発生する。**AC-4 / AC-5 は「今ある不具合の修正」ではなく「将来の脆さへの保険」**である。

この整理自体は plan.md / ADR-001 が正直に書いており評価できる。ただし AC 表の由来欄が AC-3/4/5 とも「Issue 修正案 1」となっているため、**要件由来の基準に見えてしまう**。由来を「再発防止（推定原因は否定済み）」等に改めると、スコープの内訳が読み手に正確に伝わる。S-004 の分割提案もこの整理に基づく。

## 良い点

- **推定原因を鵜呑みにせず、コードで否定した上で計画を組み立てている。** `shutdown()` に `await` が無いこと、Hono の `streamSSE` が `clients.add` まで同期であることまで確認して「Issue のシナリオは成立しない / 真因は未特定」と結論づけたのは、この計画の最大の価値。通常はここで「推定原因を潰して完了」としてしまい、要件（必ず終了する）が保証されないまま閉じられる。
- **「原因未特定だからこそタイムアウトが唯一の保証」という位置づけが正しい。** タイムアウトを「誤魔化し」ではなく主保証、構造対策を副次的な再発防止と明示的に役割分担した ADR-001 の判断は、要件充足の観点から正解。
- **`withTimeout` を切り出す動機がテスト可能性である点。** 「実サーバーでは再現できない状況を単体テストで注入する」という設計判断により、要件の中核が決定的に検証可能になっている。ここを `src/server/index.ts` にインライン実装していたら AC-1 は手動確認頼みになっていた。
- **タイムアウト発火時の `logger.warn`（AC-2）を用意した点。** 「構造対策で直ったのか、タイムアウトに救われているだけなのか」を切り分ける唯一の手段を、真因未特定という前提から逆算して用意している。P-003 で検証ステップの紐づけは要修正だが、基準の存在自体は的確。
- **`process.exit` をサーバー層に持ち込まない判断（ADR-001）。** Issue の修正案 2 をそのまま実装すると `src/server/index.ts` から `process.exit(0)` を呼ぶことになり、テストでランナーごと落ちる。Issue の文面より層責務を優先した判断は妥当で、しかも要件は既存 CLI 経由で満たされる。
- **`closeAllConnections()` が省略不可である理由（Hono の `stream.close()` は writable を閉じるだけでソケットは keep-alive に戻る）を突き止めている。** ADR-002 のこの記述は、素朴に「SSE を閉じたのだから `server.close()` は解決するはず」と考えて手順を削ってしまう事故を防いでいる。
- **スコープ「含まれないもの」が明示され、かつ各項目に理由が付いている。** graceful drain 不要・keep-alive 間隔据え置き・クライアント側変更なしの 3 点は、いずれも要件から見て正しい線引き（クライアント側の記述は P-002 の補足が必要）。
