TC-009 で検出した以下は**変更と無関係の既存の不具合**であり、Phase 5 でスコープ外 Issue として起票する:

### 既存不具合の詳細と切り分け

`http://localhost:PORT/a.md` に直接アクセスした状態でファイルを編集すると、SSE イベント自体は届くが本文が更新されず、コンソールに `[peek] Failed to fetch content: HTTP 400` が出る。

**この PR の回帰ではないと判定した根拠**（3 点、いずれも実測）:

1. `curl -N /sse` の生ストリームで、スクラッチパッド（`/private/tmp/...`）と `$HOME` 配下の通常ディレクトリの**両方**で編集時に `event: file-changed` + `event: tree-changed` が流れた。サーバー側ブロードキャストは健全で、`/private/tmp` シンボリックリンクによる監視差も無い
2. ツリーからファイルを開いた通常導線（`location.pathname === "/view"`）では、変更後ビルドで本文が更新され、ファイル追加/削除でツリーも追随。HTML ファイルモードでも同様
3. **`origin/main`（46cc093）のビルドでも全く同じく未反映＋同じコンソールエラー**。したがって `/sse` ハンドラの 503 早期拒否・`clients.add` の `!closed` ガード・`node:timers/promises` 化とは無関係

疑わしい箇所: `src/client/hooks/use-sse-updates.ts`（`getCurrentPath` 未設定で file モード分岐に落ちる疑い）、`src/server/routes/api.tsx` の `resolveAndValidatePath()`。

## testing.md の修正

TC-007 の実行中に、testing.md エッジケース 2 の期待結果が実測と食い違っていることが判明したため修正した。**テスト手順の問題であって実装の不具合ではない**ため Issue は起票せず、その場で直した。

- パイプライン全体に SIGINT を送る（＝実 Ctrl+C 相当）と `tee` が先に死ぬため、**シャットダウンの出力は丸ごとログから消える**。これは POSIX パイプの意味論であって peek の欠陥ではない
- 「短い出力は欠落しない」ことを確認したい場合は、`tee` を生かしたまま peek の PID にだけ SIGINT を送る手順が必要
- 修正: 手順に条件を 1 つ追加し、期待結果を 2 条件で書き分け、ADR-007 の本丸（読み手を先に殺して真の broken pipe を作る）を確認ポイントに明記

## 真因についての結論

**この検証は元の事象を再現していない。** 37 試行すべてが 38〜51ms で正常終了し、ハングは 1 回も観測されなかった。

条件を変えても結果は変わらなかった:

- 接続数 0〜4 本 / 放置時間 5〜663.8 秒 / ディレクトリ・HTML 両モード
- Node v22.22.1 / **v24.18.0**（報告者環境は v24.15.0、パッチ差のみ）
- ループバック / **LAN IP 経由の実ソケット**
- TTY / リダイレクト / パイプ / 真の broken pipe

したがって本検証で言えるのは「**修正後のコードは、報告された再現条件を含む幅広い条件で有限時間に終了する**」までである。真因が構造対策によって消えたのか、そもそも別の要因だったのかは区別できない。

**タイムアウト警告が 0/37 だった意味**: testing.md が「真逆の結論になる」と指摘していた分岐のうち、「**構造対策で足りていた**」側。`server.close()` はタイムアウト打ち切りに救われているのではなく、構造対策そのもので完結している（38〜51ms は既定予算 2000ms の 1/40〜1/50）。

**再発した場合に見るべきもの**: タイムアウト警告の有無。警告が出ていれば `server.close()` が本当に解決していない（真因が生きている）、出ずにハングするなら `shutdown()` の外側に別の原因がある。
