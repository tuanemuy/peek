## 「3 タブ」の実現方法

**3 タブ方式を採用した**（3 つの別セッションによる代替は使っていない）。

```
agent-browser --session verify-tc-003 open http://localhost:3011
agent-browser --session verify-tc-003 tab new && agent-browser --session verify-tc-003 open http://localhost:3011
agent-browser --session verify-tc-003 tab new && agent-browser --session verify-tc-003 open http://localhost:3011
```

`tab list` は放置の全期間を通じて 3 タブとも `http://localhost:3011/` を指したままだった（`about:blank` への巻き戻りは発生していない）。

```
  [t1] localhost:3011 - http://localhost:3011/
  [t2] localhost:3011 - http://localhost:3011/
→ [t3] localhost:3011 - http://localhost:3011/
```

## 各接続が実際に張られていることの確認方法

以下の 4 系統で確認した。

1. **peek プロセス側の ESTABLISHED 接続数（`lsof -nP -a -p <peek pid> -iTCP:3011 -sTCP:ESTABLISHED`）**
   ブラウザを開く前のベースラインが **0**、3 タブを開いた直後に **3**、`curl -N` を併張して **4** になった。
   さらに重要なのは、**放置の全期間で同じ FD・同じクライアントポートが維持された**ことである。

   | 時点 | 本数 | クライアントポート |
   |---|---|---|
   | 3 タブ直後 | 3 | 61638 / 61640 / 61661 |
   | `curl -N` 併張直後（放置開始 t=0） | 4 | 61638 / 61640 / 61661 / **61679(curl)** |
   | t=132s | 4 | 同一 |
   | t=310s（5 分時点） | 4 | 同一（FD 15u/16u/17u/18u も同一） |
   | t=649s（SIGINT 直前） | 4 | 同一 |

   ポート番号と FD が一度も変わっていない＝**途中で切れて再接続したソケットは 1 本も無い**。

2. **`agent-browser network requests --filter sse`（再接続の有無の否定的証拠）**
   放置開始時点で `/sse` のエントリは **3 件のみ**（`[10796.8]` / `[10800.8]` / `[10802.8]`、いずれも `(EventSource) 200`、ページ ID が 3 つとも異なる＝ 1 タブ 1 本）。
   **t=310s でも t=649s でも 3 件のまま増えていない**（SIGINT 直前の生存確認プローブで 1 件増えて 4 件。後述）。
   再接続が起きていればここにエントリが積まれるので、これが「pending のまま維持されている」ことの直接的な証拠になる。

3. **`agent-browser console`（再接続ログの不在）**
   `src/client/lib/sse.ts` は再接続のたびに `[peek] SSE reconnecting in {delay}ms (n/10)...` を `console.log` する。
   放置中は **console が終始空**だった（＝ `onerror` が一度も発火していない）。
   参考として、SIGINT 後は同じ console に `SSE reconnecting in 1000ms (1/10)...` 以降が出ており、
   **ログ経路自体は生きていたのに放置中は 1 行も出なかった**ことが確認できる。

4. **SIGINT 直前のページ状態とプローブ `EventSource`（指示による直前確認）**
   3 タブそれぞれで `eval` した結果、全タブが `href=http://localhost:3011/` / `title=consecutive-elements.md - peek` / `readyState=complete`。
   加えてタブ 3 で `new EventSource("/sse")` のプローブを張って `onopen` を待ち、**`probeReadyState=1`（OPEN）**を確認して `close()` した
   （この 1 本が `network requests` の 4 件目 `[10802.9]`。close 後に ESTABLISHED が 4 本へ戻ったことも確認済み）。
   `snapshot --max-output 8000` でファイルツリー（`File navigation` / `Search files` / `edge-cases` 配下）が正しく描画されたままであることも確認した。

## keep-alive が実際に流れていた証拠

`curl -sN --no-buffer http://localhost:3011/sse` を 1 本併張し、受信行に `systime()` を付けて記録した。

- レスポンスヘッダ: `HTTP/1.1 200 OK` / `content-type: text/event-stream` / `transfer-encoding: chunked`
- **受信した `: keep-alive` 行数: 22 行**
- 最初の keep-alive: `1784975531`（放置開始 t=+27s）
- 最後の keep-alive: `1784976161`（放置開始 t=+657s、SIGINT の 6.6 秒前）
- 間隔: 最初から最後まで **630 秒 ÷ 21 区間 = ちょうど 30.0 秒**（欠落・再送なし）

期待した「keep-alive を 20 周以上」に対して **21 周分（22 行）**を実測した。
すなわち ADR-006 が解消した abort リスナーリークが仮に残っていれば、**1 接続あたり 21 回分**蓄積している条件で SIGINT を送っている。

### TC-001 との比較（非退行の判定）

| 条件 | SSE 接続数 | 放置時間 | 所要時間 |
|---|---|---|---|
| TC-001 試行 1（ブラウザのみ） | 1 | 70s | 42ms |
| TC-001 試行 2〜10（ブラウザ + curl） | 2 | 70s / 5s | 38〜40ms |
| **TC-003（本項目）** | **4** | **663.8s** | **44ms** |

TC-001 の 38〜42ms に対して **44ms**。差は +2〜6ms で、`node -e Date.now()` の起動コスト（数十 ms 単位で揺れる）に埋もれる水準であり、
**接続数 4 倍・放置時間 9.5 倍に対して所要時間は有意に増えていない**。
仮に abort リスナーが keep-alive 周期で蓄積していれば、21 周 × 4 接続分の後始末が SIGINT 時に効いてくるはずだが、その兆候は一切観測されなかった。
期待結果「タブ数・放置時間に比例して遅くならない」を満たす。

### この観測の意味

本項目は Issue の症状プロファイル（「タブを長く開いているほど踏みやすい」「`--host 0.0.0.0` で複数クライアント」）に最も近い条件である。
その条件で **タイムアウト警告 0 件・44ms で完了**したことは、シャットダウンが 2000ms の打ち切りに救われているのではなく、
**構造対策（ADR-006 の abort リスナー整理と `closeAllConnections()`）だけで完結している**ことを意味する。
「放置時間が効く唯一の条件」で非退行が確認できたため、TC-001 の結論（警告 0 件）が短時間放置に依存した偶然でないことも裏づけられた。

## 失敗詳細

なし。

### 判定に影響しない記録事項

- **最初の起動を 1 度やり直している。** 当初は `nohup ... &` で peek を起動したが、この形態では後続シェルから `wait` で終了ステータスを回収できず、
  期待結果の「exit code 0」を厳密に確認できないことに放置開始から約 4.5 分の時点で気づいた。
  そこで**その試行は破棄し**（peek・`curl`・agent-browser セッションをすべて片付け）、起動と `wait` を同一シェルに置く構成で**放置を最初からやり直した**。
  本レポートに記載した放置時間 663.8 秒・keep-alive 22 行は、すべて**やり直し後の 1 本のセッションでの実測値**であり、破棄した試行の時間は含まない。
- SIGINT 直前の生存確認プローブ（`new EventSource("/sse")`）は一時的に 5 本目の接続を作るが、`onopen` 確認後すぐ `close()` しており、
  SIGINT 時点の接続数は 4 本に戻っている（`lsof` で確認済み）。
- 確認したのは**ディレクトリモード（`src/client/lib/sse.ts`）**のみ。HTML ファイルモードは TC-002 の対象。
