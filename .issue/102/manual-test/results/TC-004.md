## 再接続の観測方法

指示どおり `agent-browser --session verify-tc-004 network requests` を第一候補として使い、**時刻の精度を補うために 3 系統を併用**した。

1. **`agent-browser network requests --filter sse`（主: 試行回数の確定）**
   `EventSource` のリクエストがそのまま記録される。ただし行頭の `[6837.8]` は**時刻ではなく `ページID.リクエスト連番`** である
   （`fetch` でマーカーを 1 本撃って確認: 連番だけが `.10` に進み、`Date.now()` との対応が取れなかった）。
   したがって**このコマンドからは「何回試行されたか」「初回だけ 200 で以降はステータスなし（＝接続失敗）」しか読めない**。
2. **ページ内 `EventSource` コンストラクタのラッパー（主: 試行時刻の確定）**
   SIGINT 前に `eval` で `window.EventSource` を関数でラップし、呼び出しごとに `Date.now()` を `window.__sseLog` に積む。
   `src/client/lib/sse.ts` の `connect()` は再接続のたびにグローバルの `new EventSource("/sse")` を呼ぶため、
   **リトライは全数このラッパーを通る**（ページ読み込み時に張られた初回接続だけはラッパー設置前なので記録されない）。
   これが**ミリ秒精度の試行時刻**を与える唯一の手段だった。
   ```js
   window.__sseLog = [];
   const O = window.EventSource;
   const W = function(url, cfg) { window.__sseLog.push({t: Date.now(), url: String(url)}); return new O(url, cfg); };
   W.prototype = O.prototype; window.EventSource = W;
   ```
3. **`agent-browser console`（裏取り: リトライ回数と待機時間）**
   `src/client/lib/sse.ts` の `logger.info` / `logger.warn` が `console.log` / `console.warn` に出るため、
   `[peek] SSE reconnecting in {delay}ms ({n}/10)...` と打ち切りの警告をそのまま読める。

> Resource Timing（`performance.getEntriesByType('resource')`）は TC-001 の記録どおり `EventSource` を記録しないため使用していない。
> 観測中はページの再読み込み・タブ操作・`network requests --clear` を一切行っていない（試行回数の数え直しを防ぐため）。

## 理論値の再計算（`src/core/sse-constants.ts` を自分で読んで算出）

```ts
export const SSE_MAX_RETRIES = 10;
export const SSE_INITIAL_RETRY_MS = 1000;
export const SSE_MAX_RETRY_MS = 30000;
export const SSE_STABLE_THRESHOLD_MS = 5000;
```

`src/client/lib/sse.ts` の `onerror` は `retryCount++` → `delay = min(1000 * 2^(retryCount-1), 30000)` → `setTimeout(connect, delay)`。
接続は即座に `ERR_CONNECTION_REFUSED` で失敗するため `SSE_STABLE_THRESHOLD_MS`（5000ms）の安定判定タイマーは毎回 `onerror` 内でクリアされ、
`retryCount` はリセットされない。累積時刻は次のとおり。

| n | delay(ms) | 累積 t(ms) |
|---|---|---|
| 1 | 1000 | 1000 |
| 2 | 2000 | 3000 |
| 3 | 4000 | 7000 |
| 4 | 8000 | 15000 |
| 5 | 16000 | 31000 |
| 6 | 30000（上限） | 61000 |
| 7 | 30000 | 91000 |
| 8 | 30000 | 121000 |
| 9 | 30000 | 151000 |
| 10 | 30000 | 181000 |

10 回目（t=181000ms）の接続が失敗すると `retryCount` が 11 になり `retryCount > SSE_MAX_RETRIES` で打ち切り。**11 回目は存在しない。**

## 観測サマリー

- **最初の再接続までの時間: 1014ms**（期待「30 秒待たずに」に対して **約 1/30**）。keep-alive の 30 秒周期を待たずに切断が検知されている。
- **再接続の試行時刻（ms）: 1014 / 3019 / 7027 / 15037 / 31046 / 61056 / 91065 / 121075 / 151078 / 181090**
  → 理論値 1000 / 3000 / 7000 / 15000 / 31000 / 61000 / 91000 / 121000 / 151000 / 181000 と**全点一致**（最大 +90ms）。
  バックオフが `min(1000*2^(n-1), 30000)` どおりに指数増加し、6 回目以降 30 秒で頭打ちになっていることも `console` の待機時間表示で裏取り済み。
- **10 回で停止: YES。** 11 回目は観測されず、`SSE connection lost after 10 retries, giving up.` で明示的に打ち切られた。無限再接続は発生しない。
- **503 は観測されず**（testing.md の予告どおり）。`server.close()` がシャットダウン冒頭で走るため、以後の試行は TCP レベルで拒否され HTTP ステータスに到達しない。**確認ポイントに従い、これを異常とは扱わない。**
- peek 側: **43ms で終了・タイムアウト警告 0 件**（TC-001 の 38〜42ms と同水準）。

### この観測の意味

自動テスト（`sse.test.ts`）が担保するのはサーバー側の 503 応答と body の EOF までである。本項目で初めて、
**実ブラウザの `EventSource` が (i) サーバー停止をほぼ即座（14ms 程度）に検知し、(ii) 上限 10 回・指数バックオフで確実に停止する**
ことが実測で確認できた。`src/core/sse-constants.ts` の定数がクライアント実装で意図どおりに使われており、
シャットダウン後にブラウザが無限にリクエストを撃ち続ける状態にはならない。

## 失敗詳細

なし。

### 判定に影響しない記録事項

- **peek の exit code は本項目では取得していない。** 本項目は `nohup ... &` で起動したため、後続シェルから `wait` で終了ステータスを回収できない
  （TC-003 ではこの点を改め、起動と `wait` を同一シェルに置く構成で計測している）。プロセスは SIGINT から 43ms で消失し、
  ログに `┌ Shutting down...` / `└ Server stopped. Bye!` が正常な順序で出ており、`Force exiting...`（exit 1 経路）は出力されていない。
  終了性そのものは TC-001 の 10 試行および TC-003 で exit code 0 として別途確認済み。
- 確認したのは**ディレクトリモード（`src/client/lib/sse.ts`）の 1 実装**のみ。HTML ファイルモードのインラインスクリプト側は
  同じ `sse-constants.ts` を参照するが、本項目では未確認（TC-002 の対象範囲）。
