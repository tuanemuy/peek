ADR-001 が「真因切り分けの唯一の手掛かり」と位置づけた 2 つの観測が、実運用の出力に実際に現れるかを確認する。

## 判定

### 1. シグナル受信ログ — PASS

**37/37 の全試行で `[peek] Received SIG{INT,TERM}, shutting down...` が出力された。**

これは調査結果で挙がっていた可能性 (ii)「**そもそも SIGINT ハンドラが起動していなかった**」の否定にあたる。TC-006 のエッジケース 3 では `Received SIGTERM`（`SIGINT` ではない）が出力され、シグナルの識別も機能していることを確認した。

### 2. タイムアウト警告 — PASS（正常系で偽陽性なし）

**37/37 の全試行でタイムアウト警告は出力されなかった。**

これは testing.md の確認ポイントが「毎回警告なし」と「毎回警告あり」で真逆の結論になると指摘していた分岐のうち、**前者**にあたる:

> 「毎回警告なし」＝構造対策で足りていた／「毎回警告あり」＝真因が生きたままタイムアウトに救われている

**観測された所要時間は 38〜51ms** で、既定のシャットダウン予算 2000ms に対して 40〜50 倍のマージンがある。`server.close()` はタイムアウト打ち切りに救われているのではなく、構造対策そのもので完結している。

条件を変えても結果は変わらなかった:

- 接続数: 0 本 〜 4 本（TC-006 ベースライン 〜 TC-003 の 3 タブ + curl）
- 放置時間: 5 秒 〜 663.8 秒（keep-alive 21 周）
- モード: ディレクトリ / HTML ファイル
- Node: v22.22.1 / v24.18.0
- ソケット: ループバック / LAN IP 経由

### 3. clack の枠描画 — PASS

**37/37 で `┌ Shutting down...` 〜 `└ Server stopped. Bye!` の枠が正常**に描画され、警告行による割り込みも発生しなかった（警告自体が 0 件のため）。TC-001 では `^C` エコーとの行連結が起きていないこと（`console.log()` による空行が保たれていること）も確認した。

## 真因についての示唆

この検証は**元の事象を再現していない**。37 試行すべてが 38〜51ms で正常終了し、ハングは 1 回も観測されなかった。

したがって本検証で言えるのは「**修正後のコードは、報告された再現条件（`--host 0.0.0.0`、SSE 接続あり、ブラウザタブ長時間オープン、Node 24）を含む幅広い条件で有限時間に終了する**」までである。真因が構造対策によって消えたのか、そもそも別の要因（Node のパッチバージョン差など）だったのかは、この検証では区別できない。

**再発した場合に見るべきもの**: タイムアウト警告の有無。警告が出ていれば `server.close()` が本当に解決していない（真因が生きている）、出ずにハングするなら `shutdown()` の外側に別の原因がある。
