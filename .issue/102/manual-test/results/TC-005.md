### `nix shell` のラッパープロセスについて（重要）

指示のとおり `pgrep -f "dist/index.mjs .*--port 3013"` で peek 本体の実 PID を特定してから `kill -INT` した。実測の結果、

- **`$!`（`nix shell ... -c` を起動したシェルが返す PID）と `pgrep` で得た peek 本体の PID は全 3 試行で一致した**
  （試行 1: 81906 / 試行 2: 85480 / 試行 3: 86192、いずれも `wrapper_pid == real_pid == target_pid`）。
- 試行 2 で peek プロセスの親を確認したところ `/bin/bash`（起動スクリプト）で、**間に nix のラッパープロセスは残っていない**。
  すなわち `nix shell ... -c` は最終的に `node` へ exec しており、シグナルは中継されずに直接届く。
- したがって **ラッパー経由かどうかで挙動が変わる事象は観測されなかった**（`wait $!` で取得した exit code も peek 自身のもの）。

## SSE 接続の確認方法

TC-002 と同一の 4 系統で確認した（全 3 試行で実施・記録）。ディレクトリモードなので SSE クライアントは `src/client/lib/sse.ts` 側の実装。

1. **ブラウザのネットワーク記録（`agent-browser network requests --filter sse`）** — 主たる証拠。
   全 3 試行で `GET http://localhost:3013/sse (EventSource) 200` を記録。
2. **`agent-browser eval` によるトップレベル文書の確認**
   全 3 試行で `{"url":"http://localhost:3013/","top":true,"inlineSse":true}`。
3. **サーバー側 ESTABLISHED 接続数（`lsof -nP -iTCP:3013 -sTCP:ESTABLISHED`）**
   起動前ベースライン **0** → ページを開いた直後 6 エントリ → 放置後の SIGINT 直前は **4 エントリ（2 ペア）
   = `node ↔ Google Chrome` 1 本 + `node ↔ curl` 1 本**。試行 1 ではこの状態が **70 秒放置後も維持**されていることを確認。
4. **保証用の `curl -N http://localhost:3013/sse` 併張** — 全 3 試行で `HTTP/1.1 200 OK`。

`snapshot --max-output 8000` は全 3 試行で 8086 bytes を取得し、ファイルツリー（`File navigation` / `Search files` / fixture 配下のリンク群）が描画されていることを確認した。

### この観測の意味

「真因の残る有力な変数」とされた **Node のメジャーバージョン差（22 → 24）による終了性の劣化は観測されなかった**。Node 24.18.0 での 40〜42ms は、同条件・同モード（ディレクトリモード）の TC-001（Node 22.22.1、10 試行 38〜42ms、警告 0/10）と**実質的に同一**であり、シャットダウンは Node 24 でも `server.close()` の 2000ms 期限に一度も到達していない。

ただし限界として次を明記する。

- **パッチバージョンが報告者環境と異なる**（報告者 v24.15.0 / 本試行 v24.18.0）。この差で再現性が変わる可能性は本試行では否定できない。
- `kill -INT` は testing.md の表のとおり `^C` エコーとプロセスグループ配送を再現しない。対話端末での実 `Ctrl+C` による Node 24 での確認は本試行の範囲外。
- 試行回数は 3 回、うち長時間放置（70 秒）は 1 回。低頻度でしか起きない事象の否定には至らない。
