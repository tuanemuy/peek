## SSE 接続の確認方法

**testing.md / 指示が第一候補としていた `performance.getEntriesByType('resource')` は使えなかった。** 事前プローブで
`performance.getEntriesByType('resource').map(r => r.name)` を評価したところ、返るのは `http://localhost:3009/favicon.ico`
のみで、`EventSource` のリクエストは Resource Timing に一切記録されない（Chromium の仕様）。指示にある
`...filter(r => r.name.includes('/sse')).length` は常に `0` を返すため、SSE 接続の有無の判定には使えない。

そこで以下の **3 系統を併用**して確認した（すべて全 10 試行で実施・記録）。

1. **ブラウザ側プローブ EventSource（`agent-browser eval`）**
   ページ内で `new EventSource('/sse')` を張り、`onopen` を待って `readyState` を読む。
   全 10 試行で `probeReadyState=1`（`OPEN`）= **そのブラウザ／そのオリジンから実際に SSE ストリームが確立できている**。
   読み取り後は `es.close()` してプローブ分の接続は畳んでいる。
2. **サーバー側 ESTABLISHED 接続数（`lsof -nP -iTCP:3009 -sTCP:ESTABLISHED`）**
   ブラウザを開く前のベースラインが **0**、`http://localhost:3009` を開いて networkidle 到達後に **1 本が永続的に残る**ことを確認。
   この 1 本は 70 秒放置後も維持されており（試行 1 の `PRE_SIGINT_ESTABLISHED`）、通常の HTTP keep-alive アイドル接続では
   説明できない（サーバー既定の keepAliveTimeout を超えて生存している）＝ ページ自身が張った `/sse` ストリームである。
3. **保証用の `curl -N` SSE クライアント（試行 2〜10）**
   `curl -sN http://localhost:3009/sse` をバックグラウンドで張り、`HTTP/1.1 200 OK` が返って接続が保持されることを確認。
   SIGINT 直前の ESTABLISHED 数が **2**（ブラウザの `/sse` + curl の `/sse`）であることを毎試行記録した。
   **ブラウザは終始開いたまま維持**しており、`snapshot --max-output 8000`（8086 bytes）でファイルツリーが描画されていることも毎試行確認している。

> 試行 1 のみ `curl -N` 併用前に実施したため SSE クライアントは**ブラウザ 1 本のみ**。試行 2〜10 は**ブラウザ + curl の 2 本**。
> 参考として、ライブリロード経由の確認（fixture の Markdown に見出しを追記して DOM に反映されるか）も試したが、
> 4 秒待っても `document.body.innerText` にマーカーが現れず、この方法では SSE 接続の存在を肯定的に示せなかったため採用していない。
> （TC-001 の判定対象外だが、ライブリロードの挙動として別途確認する価値がある事象として記録しておく。）

## 観測サマリー

- 所要時間: **最小 38ms / 最大 42ms / 中央値 39ms**（全 10 試行が期待値 5000ms に対し 3 桁のマージン）
- exit code: **10/10 が 0**
- `[peek] Received SIGINT, shutting down...`: **10/10 で出力**（＝ 調査結果の可能性 (ii)「そもそもハンドラが起動していなかった」は否定される）

- **タイムアウト警告: 0/10 回**（← 最重要）
- ハング: **0/10 回**（10 秒ウォッチドッグ発火 0 回、`kill -9` を要した試行 0 回）

### この観測の意味

testing.md 確認ポイントの「毎回警告なし／毎回警告あり」の二分において、本試行はすべて**警告なし**だった。
すなわち **`server.close()` は毎回 2000ms の期限を待たずに（実測で数十 ms 以内に）完了しており、
シャットダウンはタイムアウト打ち切りに救われているのではなく、構造対策そのもので完結している**。
「真因が生きたままタイムアウトに救われている」側の兆候は本条件では一切観測されなかった。

ただし本試行が埋めた条件は「macOS × 実ブラウザ SSE × Node 22 × `kill -INT`」であり、
`kill -INT` は testing.md の表のとおり `^C` エコーとプロセスグループ配送を再現しない。
報告者環境の Node 24 系（確認項目 6）と、対話端末での実 `Ctrl+C`（確認項目 1 の人手実施分）は別途必要である。

## 失敗詳細

なし（FAIL 試行 0 件）。

### 補足: TC-001 の判定には影響しない観測事項

事前プローブでライブリロードの確認を試みた際、peek を fixture ディレクトリで起動しブラウザで
`http://localhost:3009/01-headings.md` を開いた状態で、当該 Markdown に見出し行を追記して 3〜4 秒待っても
DOM（`document.body.innerText`）に追記内容が反映されなかった（2 回試行、いずれも未反映）。
`/sse` 接続自体は確立しており（`readyState=1`、ESTABLISHED 維持）、TC-001 の判定対象（シャットダウンの終了性）には
影響しない。ただし testing.md「既存機能への影響確認」のライブリロード項目に該当しうるため、
**別途その項目で追試する必要がある**。fixture が scratchpad 配下（`/private/tmp/...`）にあることによる
ファイル監視の挙動差の可能性もあり、本結果だけでライブリロードの不具合とは断定しない。
